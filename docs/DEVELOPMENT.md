# 开发与验收

## 规则

保留原 PDF 与论文身份。异步请求必须绑定当前论文和请求生命周期，切篇或取消后的迟到结果不得覆盖新篇。源文本未核对时不能创建看似准确的定位；图像位置、题注与正文提及句需要区分。

局部追问与研究讨论分别存储。没有实际发送的局部输入不能成为一条历史对话。重构时保留用户记录及旧结构迁移备份，不把清理旧 UI 变成删用户数据。

## 检查层级

1. `npm run check`：构建同步、实际函数的离线行为、语法和打包边界。
2. 浏览器：真实 PDF 导入、划选、外点、缩放、分栏、滚动恢复、公式字体与来源定位。
3. 宿主：确认运行中的代码版本与磁盘一致，再测试真实模型。
4. 内容审核：同一篇论文先由独立评审直接读原文，冻结基线后再看插件输出，记录准确性、覆盖、依据、可执行性与定位差异。

记录每项的源码版本、输入范围、真实／固定响应、耗时和失败。保留失败原报；修复测试夹具不等于修复产品。每轮只在有变更或未解决疑问时重跑相关用例。

## 已知待核对项

- PDF 数学文本可能被线性化；公式可视化不等于完整恢复原 PDF 的二维结构。
- 个别图表、题注、正文提及和跨页文献仍需要进一步核对。
- 结构解析的大批量通过不等于逐篇内容完整性或模型质量通过。
- 浏览器与宿主的性能、缩放比例和视口不同，需要分别记录。
- 研究建议必须交代操作机制、推理阶段输入与依赖、对照和失败条件，不能只列指标就称为可执行方案。

历史本地材料不进入源码分发。新增测试优先使用自造文本或程序生成的最小 PDF；真实论文的使用与再分发权限应独立核对。
